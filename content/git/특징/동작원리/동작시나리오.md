# 파일추가 
파일이 추적되려면 먼저파일이 git의 데이터베이스에추가돼있어야함

커밋은 git 데이터 베이스 안의 파일에 대한 변경사항을 기록 

git add
주어진 파일의 스냅샷을 만들어 저장소에 저장함으로써 나중에 커밋할 때 참조할 수 있게 함 

git이 앞으로 한번도 커밋되지 않을 스냅샷도 저장 

스냅샷은 디스크 공간을 아주 작게차지하고 가비지컬렉션을수행

가비지 컬렉션 
어떤커밋으로부터 참조되지않는 객체를 찾아내 삭제하는 기법 

뜨내기 객체에 의해 표현되는 작업에 불과하므로 커밋안한 거라가 

저장할가치가있는작업이었다면커밋했을거라고 gitㅡㅇㄴ 가정


staging 
- 
git add로 새버전이 git 데이터베이스에추가

staging area
파일을 올린후커밋하기 전까지 새 버전이 대기하는 장소 
- 다른 사람과 공유되거난 동기화 되지 않으며 오직 로컬 컴퓨터에만 존재 

스테이징시 일어나는일

1.  git은 그 파일의 스냅샷을 데이터베이스에 저장해 다음 커밋할 때 참조될 수 있게함

git에선 본질적으로 파일이 참조될 수 있도록 이미 저장소에 존재해야함
커밋할 때 반드시 참조돼야함

파일의버전이 스테이징되기전에는 gitㅡㅇㄴ 그 버전을 알 수 없으며 따라서 커밋도 할 수 없음 

2. git은 다음 커밋의 로컬초안을 작성 
- 안에 있는 모든 파일과 디렉터리 참조가 포함 
공교롭게도 이전 커밋으로부터 덮어쓰거나 변경되지않은 파일의 참조도 포함 
모든커밋은 보수적
단지변경된 대상만참조하지않고 특정시점에서 프로젝트의 상태를 구성하는 모든 것을 참조 


  

# git의 명령어의 작동 이해하기

objects와 refs의 변화
- objects: 파일의 데이터가 같은 경우를 제외한 다른 blob/tree/commit 정보들이 추가된다.
- refs: 새로 생긴 remotes의 branch들을 추가하고, commit이 된 경우에는 각 브랜치 별로 최신 커밋으로 참조값을 수정해줘야 한다.
-   refs의 폴더 구조는 위와 같이 구성되며, git에서 관리하는 branch들의 정보가 들어 있다. 로컬에서 작업하는 부분은 heads, 원격 저장소는 remotes 안에 관리 된다. 각 브랜치별 마지막 커밋의 해시값을 저장하고 있다.




# 예시

  

test 디렉터리에 git init를 한 뒤에, hello.txt를 만들고 "안녕 나는 공부중이야" 를 저장한다. 그 뒤 git add하고 git commit한다. 마지막으로 git tag를 한다. 이 과정중에서 생성되는 object들을 보자.


1. blob
git add할 때 생성된다. 파일 내용이 들어 있다

2. tree
git commit할 때 생성된다. 타입과 객체명, 파일명이 기록된다.

3. commit
git commit할 때 생성된다. tree객체명, 부모commit객체명, author, committer, message를 기록한다. 이는 commit할때 git config에 있는 name과 email이 찍히는 거다.

4. tag
git tag할 때 생성된다. commit 객체명, tag이름, tagger, message가 기록된다.
