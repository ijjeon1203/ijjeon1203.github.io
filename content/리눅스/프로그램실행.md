꼭 테라텀을 3개 띄울 필요는 없습니다.

상황에 따라 방법이 다릅니다.

### 1. 백그라운드 실행 (`&`)

```bash
./program1 &
./program2 &
./program3 &
```

이렇게 하면 한 터미널에서 여러 프로세스가 동시에 실행됩니다.

실행 중 확인:

```bash
jobs
```

또는

```bash
ps -ef | grep program
```

---

### 2. 다른 터미널 사용

테라텀을 여러 개 띄워서 각각 접속하는 것도 가능합니다.

```text
TeraTerm #1 → program1
TeraTerm #2 → program2
TeraTerm #3 → program3
```

가장 단순한 방법입니다.

---

### 3. screen 사용 (서버 작업 시 추천)

```bash
screen -S server1
./program1
```

새 세션:

```bash
screen -S server2
./program2
```

목록 확인:

```bash
screen -ls
```

재접속:

```bash
screen -r server1
```

SSH가 끊겨도 프로그램이 계속 동작합니다.

---

### 4. tmux 사용 (가장 추천)

세션 생성:

```bash
tmux new -s test
```

창 분할:

```bash
Ctrl+b %
```

또는

```bash
Ctrl+b "
```

한 화면에서 여러 프로그램을 동시에 실행할 수 있습니다.

---

Jetson이나 Linux 보드에서 **장시간 실행하는 서버 프로그램**이라면 단순히 테라텀 여러 개보다는 `tmux` 또는 `screen`을 사용하는 것이 훨씬 편합니다. SSH가 끊겨도 프로세스가 살아있기 때문입니다.


네. 단순히 `&`로 실행하면 프로그램은 백그라운드로 가지만 **stdout/stderr 출력은 여전히 현재 터미널에 출력**됩니다.

예:

```bash
./server &
```

그러면 프롬프트는 바로 돌아오지만,

```text
[1] 12345
server start...
recv data...
recv data...
```

처럼 로그가 계속 화면에 찍힐 수 있습니다.


### tmux/screen 사용 시

tmux 안에서 실행하면:

```bash
tmux new -s test
./server
```

`Ctrl+b d`로 분리(detach)한 뒤,

나중에:

```bash
tmux attach -t test
```

하면 실행 중인 프로그램 화면을 그대로 다시 볼 수 있습니다.

---

즉,

* `&` → 실행은 계속되지만 터미널 화면 상태를 다시 보기 어려움
* `> log 2>&1 &` → 로그 파일로 확인
* `tmux`/`screen` → 나중에 실행 중인 화면 그대로 복귀 가능

장시간 돌리는 서버나 테스트 프로그램이라면 `tmux`가 가장 편합니다.
잠깐씩 상태만 보고 싶다면 몇 가지 방법이 있습니다.

### 방법 1. 로그 파일 + tail (가장 많이 사용)

```bash
./server > server.log 2>&1 &
```

필요할 때:

```bash
tail -f server.log
```

종료:

```bash
Ctrl + C
```

다시 보고 싶으면 또 `tail -f` 하면 됩니다.

---

### 방법 2. tmux 사용

```bash
tmux new -s server
./server
```

분리:

```bash
Ctrl+b d
```

잠깐 확인:

```bash

```

다시 분리:

```bash
Ctrl+b d
```

프로그램 화면을 그대로 볼 수 있습니다.

---

### 방법 3. 프로그램이 이미 `&`로 실행 중인 경우

실행 중인 출력 화면 자체를 다시 붙어서 보는 건 어렵습니다.

```bash
./server &
```

로 실행한 경우에는 보통:

```bash
ps -ef | grep server
```

로 살아있는지 확인하거나,

처음부터 로그 파일로 리다이렉트하는 것이 좋습니다.

---

개발/디버깅 중이라면 저는 **tmux**를 추천합니다. 테라텀은 하나만 띄워도 되고, 필요할 때만 붙어서 로그를 볼 수 있습니다. Jetson 같은 Linux 보드에서도 많이 쓰는 방식입니다.

`tmux`는 **터미널 멀티플렉서(Terminal Multiplexer)** 입니다.

쉽게 말하면 **SSH나 테라텀을 끊어도 프로그램이 계속 실행되게 해주고, 나중에 다시 그 화면으로 돌아올 수 있는 도구**입니다.

### 이미 백그라운드로 돌고 있는 프로세스

만약:

```bash
./server &
```

로 실행했는데 로그를 파일로 저장하지 않았고, 현재 터미널에서도 안 보이는 상태라면

**그 프로세스가 과거에 출력한 내용은 다시 볼 방법이 없습니다.**

왜냐하면 Linux는 기본적으로 프로그램의 stdout을 저장해주지 않기 때문입니다.

그래서 실무에서는 보통:

```bash
./server > server.log 2>&1 &
```

또는

```bash
tmux
```

를 사용합니다.

참고로 현재 `jobs`에 뜨는 프로세스가 어떤 프로그램인지 보여주시면, 지금 상태에서 로그를 볼 수 있는지 판단해드릴 수 있습니다.
네.

`jobs`에서 **Stopped**로 나오면 프로세스가 실행 중이 아니라 **일시 정지(Suspend)** 된 상태입니다.

예:

```bash
$ jobs

[1]+  Stopped    ./server
```

이 상태에서는:

* CPU 사용 안 함
* 코드 실행 안 함
* 입력 처리 안 함
* 메모리에는 남아 있음

즉, 완전히 종료된 것은 아니고 **멈춰서 대기 중**입니다.

### 왜 Stopped가 되나?

보통 다음 경우입니다.

#### Ctrl + Z 누른 경우

```bash
./server
```

실행 중

```text
^Z
[1]+ Stopped ./server
```

### 다시 실행

#### 전면(Foreground)으로

```bash
fg %1
```

#### 백그라운드로

```bash

```

확인:

```bash

```

```text
[1]+ Running ./server &
```

---

### 종료하려면

```bash
kill %1
```

또는 PID로:

```bash
kill 12345
```

---

자주 보는 상태는:

```text
Running   -> 실행 중
Stopped   -> 일시 정지
Done      -> 정상 종료
Terminated -> 강제 종료됨
```

따라서 `Stopped`가 보이면 프로그램이 죽은 건 아니고, 보통 `Ctrl+Z` 등으로 멈춰 있는 상태라고 생각하시면 됩니다.

상황에 따라 다릅니다. **무조건 삭제하면 안 됩니다.**

`/usr/src`는 일반적으로 다음과 같은 것들이 들어 있습니다.

* Linux 커널 소스
* 커널 헤더
* 드라이버 소스
* SDK 소스
* 벤더(NVIDIA, Xilinx 등) 제공 소스 코드

확인:

```bash
ls -lh /usr/src
```

를 실행하면 파일 시스템의 디렉터리 엔트리가 제거되고, 해당 파일을 참조하는 링크가 없으면 디스크 공간도 즉시 회수

아닙니다.

Linux에서 `rm`은 **휴지통을 거치지 않고 바로 삭제**합니다.

```bash

```

를 실행하면 파일 시스템의 디렉터리 엔트리가 제거되고, 해당 파일을 참조하는 링크가 없으면 디스크 공간도 즉시 회수됩니다.

확인:

```bash
df -h
```

삭제 전후로 용량이 줄어든 것을 볼 수 있습니다.

### 정리

| 방법            | 휴지통 이동 | 용량 즉시 감소         |
| ------------- | ------ | ---------------- |
| `rm file`     | ❌      | ⭕                |
| `rm -rf dir`  | ❌      | ⭕                |
| 파일 관리자 Delete | ⭕ (보통) | ❌                |
| Shift+Delete  | ❌      | ⭕                |
| 열린 파일 `rm`    | ❌      | ❌ (프로세스 종료 후 감소) |

현재 `/usr/src`를 정리하려는 거라면 `rm -rf`로 지우면 일반적으로 즉시 용량이 회수됩니다. 다만 삭제 후에도 용량이 안 줄면 `lsof | grep deleted`를 확인해보시는 것이 좋습니다.

아니요. `uname`은 검색 명령이 아닙니다.

```bash
uname
```

은 시스템 정보를 출력합니다.

예:

```text
Linux
```

또는

```bash
uname -a
```

```text
Linux jetson 5.10.104-tegra ...
```

전체 디스크에서 파일을 검색하려면 보통 `find`를 사용합니다.

### 파일 이름 검색

```bash
find / -name "파일명"
```

예:

```bash
find / -name "xdma.ko"
```

---

### 대소문자 무시

```bash
find / -iname "xdma.ko"
```

---

### 특정 확장자 검색

```bash
find / -name "*.desktop"
```

---

### 디렉터리 검색

```bash
find / -type d -name "kernel"
```

---

### 에러 숨기기

권한 없는 디렉터리가 많으므로 보통:

```bash
find / -name "xdma.ko" 2>/dev/null
```

를 사용합니다.

---

### 더 빠른 검색

`locate`가 설치되어 있다면:

```bash
locate xdma.ko
```

다만 DB 갱신이 필요할 수 있습니다.

```bash
sudo updatedb
```

---

### 특정 문자열이 들어있는 파일 찾기

예를 들어 `XDMA`라는 문자열을 포함한 파일:

```bash
grep -R "XDMA" / 2>/dev/null
```

---

전체 하드디스크에서 파일을 찾으려는 거라면 보통:

```bash
find / -name "*키워드*" 2>/dev/null
```

를 가장 많이 사용합니다.
`.o` 파일 전부 삭제라면 보통 `-r`은 필요 없습니다.

현재 디렉터리의 `.o` 파일만 삭제:

```bash
rm *.o
```

---

현재 디렉터리부터 하위 디렉터리까지 모든 `.o` 파일 삭제:

```bash
find . -name "*.o" -delete
```

또는

```bash
find . -name "*.o" -exec rm {} \;
```

---

삭제 전에 확인하고 싶다면:

```bash
find . -name "*.o"
```

---

주의:

```bash
rm -r *.o
```

는 `.o` 파일이 아니라 **디렉터리**를 삭제할 때 사용하는 옵션입니다.

만약 `*.o`에 해당하는 파일이 일반 파일뿐이라면 `-r`은 불필요하고, 경우에 따라 오류가 날 수도 있습니다.

빌드 산출물 정리라면 프로젝트 루트에서 다음이 더 일반적입니다.

```bash
make clean
```

Makefile에 clean 타겟이 정의되어 있다면 `.o`, 실행파일 등을 한 번에 정리해 줍니다.


`make: Nothing to be done for 'all'.`

메시지는 **오류가 아닙니다.**

의미:

> `all` 타겟을 만들기 위해 필요한 파일들이 이미 최신 상태라서 할 일이 없다.

예를 들어:

```makefile
all: app

app: main.o test.o
	gcc -o app main.o test.o
```

현재 상태가

```text
main.c  → main.o 생성됨
test.c  → test.o 생성됨
app     → 생성됨
```

이고 `.c` 파일이 수정되지 않았다면

```bash
make
```

결과:

```text
make: Nothing to be done for 'all'.
```

---

### 강제로 다시 빌드

#### 방법 1. clean 후 빌드

```bash
make clean
make
```

---

#### 방법 2. .o 삭제

```bash
find . -name "*.o" -delete
make
```

---

#### 방법 3. 강제 빌드

```bash
make -B
```

`-B`는 모든 타겟을 무조건 다시 만듭니다.

---

### 실행파일이 안 만들어졌는데 저 메시지가 뜨는 경우

Makefile이 잘못된 경우일 수 있습니다.

확인:

```bash
ls -l
```

```bash
cat Makefile
```

또는

```bash
make -n
```

출력을 보여주시면 왜 `Nothing to be done for 'all'`이 나오는지 분석해드릴 수 있습니다.

특히 Jetson이나 드라이버 예제에서는 `all` 타겟이 실제 실행파일을 만들지 않고 하위 디렉터리만 빌드하도록 되어 있는 경우도 있습니다.
